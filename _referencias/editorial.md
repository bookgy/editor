# Criterio editorial

Este documento define **qué merece comunicarse, por qué, con qué enfoque y cómo se relacionan las distintas piezas** del sistema editorial de Agendic.

No contiene instrucciones de estilo detalladas. Para redactar, consultar `guia-redaccion.md`.

No contiene conocimiento funcional del producto. Para confirmar hechos, consultar `_fuentes/oraculo.md`.

# 1. Misión editorial

Cada pieza debe conseguir que una empresa:

1. reconozca una situación que le importa;
2. descubra una capacidad útil de Agendic;
3. entienda para qué le sirve en la práctica;
4. visualice cómo podría utilizarla;
5. tenga un motivo real para dar el siguiente paso.

La comunicación editorial no existe para demostrar cuántas funcionalidades tiene Agendic.

Existe para **convertir capacidades del producto en utilidad comprensible**.

# 2. Principio rector

No presentar una funcionalidad por lo que es.

Presentarla por el problema que ayuda a resolver, el trabajo que simplifica o el resultado que permite conseguir.

La secuencia editorial preferida es:

**situación → fricción → cambio posible → capacidad de Agendic → beneficio → ejemplo → acción**

No todas las piezas necesitan mostrar todos los pasos, pero deben respetar esa lógica.

# 3. Qué debe conseguir el contenido

El contenido de Agendic tiene cuatro funciones complementarias.

## Descubrir

Hacer visible una capacidad que una empresa quizá no conoce.

Especialmente importante para funcionalidades existentes que pueden estar infrautilizadas.

## Entender

Explicar por qué esa capacidad importa y qué cambia en el trabajo diario.

## Aprender

Dar una idea práctica, un ejemplo, una recomendación o una forma mejor de utilizar el producto.

## Actuar

Facilitar un siguiente paso proporcionado: conocer más, revisar una configuración, probar una capacidad, consultar una guía o pedir ayuda.

Una buena pieza puede cumplir varias funciones, pero debe tener una dominante.

# 4. Qué puede convertirse en contenido

Una semilla puede nacer de:

- una nueva funcionalidad;
- una mejora con impacto perceptible para el usuario;
- una funcionalidad existente poco conocida;
- una combinación útil de varias capacidades;
- un consejo práctico;
- una forma más eficiente de trabajar;
- un caso de uso;
- una pregunta frecuente que revele valor de producto;
- un error o fricción habitual que Agendic ayuda a evitar;
- una situación estacional;
- un cambio relevante en la operativa de las empresas;
- una obligación o contexto externo cuando afecte directamente al uso de Agendic y exista una fuente autorizada;
- una historia real de cliente debidamente confirmada.

El calendario editorial no debe depender solo de novedades de producto.

Una capacidad útil sigue siendo comunicable aunque lleve tiempo disponible si una parte significativa de los clientes puede no conocerla o no estar aprovechándola.

# 5. Qué no merece una publicación propia

Evitar crear una pieza independiente cuando el único argumento sea:

- un cambio técnico interno;
- una corrección sin impacto editorial relevante;
- un ajuste menor que el usuario apenas percibe;
- un cambio estético sin consecuencia práctica;
- una función cuya utilidad no puede explicarse con claridad;
- información todavía no confirmada;
- una mejora cuya única historia sea “ahora existe”.

Las mejoras menores pueden agruparse cuando juntas forman una historia útil, por ejemplo:

- varias pequeñas mejoras que reducen pasos;
- varios cambios que simplifican una misma tarea;
- un conjunto de ajustes alrededor de un mismo flujo de trabajo.

El Editor debe ser selectivo. **No es un changelog.**

# 6. Criterio de selección

Antes de crear una semilla, responder:

- ¿Está confirmado lo que vamos a contar?
- ¿Qué problema, necesidad, oportunidad o deseo de la empresa activa este tema?
- ¿Qué cambia para la empresa gracias a esta capacidad?
- ¿Se puede explicar con un ejemplo sencillo?
- ¿Hay algo que el lector pueda hacer después?
- ¿Aporta algo nuevo respecto al contenido ya existente?
- ¿Merece una pieza propia o debería agruparse con otros temas?

Si no existe una respuesta clara a las tres primeras preguntas, no forzar la comunicación.

# 7. Territorios editoriales

Los contenidos de Agendic deberían construir de forma recurrente estos territorios.

## Ahorrar trabajo

Automatizar o simplificar tareas repetitivas, reducir pasos y evitar búsquedas innecesarias.

## Ganar control

Dar visibilidad sobre clientes, reservas, cobros, ventas, actividad, recursos o procesos.

## Ordenar la operativa

Centralizar información y conectar áreas que normalmente funcionan separadas.

## Evitar errores

Reducir duplicidades, olvidos, solapamientos, información desactualizada o procesos manuales propensos a error.

## Atender mejor

Tener más contexto, reducir interrupciones y facilitar una experiencia más continua para el cliente.

## Automatizar seguimiento

Resolver avisos, recordatorios, comunicaciones, cobros u otras acciones repetitivas cuando el funcionamiento esté confirmado.

## Adaptar el sistema al negocio

Mostrar reglas, configuraciones o combinaciones que permiten reflejar la operativa real de empresas diferentes.

## Tomar decisiones con información

Transformar actividad operativa en visibilidad útil cuando existan datos o métricas confirmadas.

## Crecer sin multiplicar el caos

Mostrar cómo la centralización, los permisos, la coordinación o la gestión de varias sedes pueden ayudar cuando una empresa aumenta su complejidad.

No utilizar estos territorios como categorías rígidas. Sirven para comprobar que el contenido construye una percepción estratégica de marca.

# 8. Arquitectura de profundidad

No todas las piezas deben explicar todo.

El sistema editorial trabaja por capas:

## Capa 1. Descubrimiento

Canales sociales y bloques breves de newsletter.

Objetivo: provocar reconocimiento e interés.

Deben responder sobre todo a:

**“¿Por qué debería importarme?”**

## Capa 2. Comprensión

Blog u otras piezas de contenido desarrolladas.

Objetivo: explicar el problema, la respuesta y el uso práctico con suficiente contexto.

Debe responder a:

**“¿Cómo me ayuda esto?”**

## Capa 3. Acción

Documentación de ayuda, instrucciones operativas o contacto con soporte cuando proceda.

Objetivo: enseñar exactamente cómo utilizar o configurar la capacidad.

Debe responder a:

**“¿Cómo lo hago?”**

Una pieza editorial no debe convertirse innecesariamente en manual de producto.

Una guía operativa no necesita volver a vender el problema desde cero.

# 9. Unidad maestra: la semilla

La **semilla** es la fuente editorial maestra de un tema.

Debe separar claramente:

- hechos funcionales;
- condiciones;
- decisión editorial;
- ejemplo;
- propuesta de valor;
- posibles líneas de comunicación.

Todas las piezas derivadas de una semilla deben compartir los mismos hechos y límites.

## Identificación

Formato de carpeta:

`AAAA-MM-NNN-contenido`

Ejemplo:

`2026-09-001-cupones-promociones`

Identificador permanente:

`AAAA-MM-NNN`

Ejemplo:

`2026-09-001`

El contador `NNN` se reinicia cada mes.

Una vez utilizado el identificador en piezas derivadas, no cambiarlo.

## Estructura recomendada de `semilla.md`

Mantener la semilla clara y compacta. No rellenar apartados por obligación.

```markdown
# [Nombre interno del tema]

## Identificación
- semilla_id: AAAA-MM-NNN
- fecha: AAAA-MM-DD
- estado: borrador | validada | publicada | archivada

- ámbito: General | Fitness | Pets | Auto | Boat | Otro

## Fuente
- rutas exactas del Oráculo utilizadas:
  - ...

## Hechos confirmados
- ...

## Condiciones y matices
- ...

## Dolor o necesidad

- consecuencia:
```

# 10. Cómo descubrir el dolor sin inventarlo

El dolor no tiene que aparecer literalmente en el Oráculo.

Puede deducirse editorialmente cuando existe una relación directa, evidente y razonable entre la capacidad confirmada y una fricción normal de empresa.

Ejemplo:

Si una capacidad permite enviar recordatorios automáticos, es razonable hablar de trabajo manual repetitivo o de la necesidad de recordar citas.

No es razonable afirmar sin evidencia que esa capacidad “reduce las ausencias un 40 %”.

Distinguir siempre:

## Inferencia editorial permitida

Explicar una consecuencia lógica del comportamiento confirmado.

## Afirmación factual no permitida

Inventar magnitudes, resultados, comportamientos de clientes, ahorros concretos o impactos que no estén demostrados.

Si el dolor requiere demasiadas suposiciones para sostenerse, buscar otro enfoque.

# 11. Propuesta de valor

La propuesta de valor debe responder a:

**“¿Qué cambia en el trabajo de la empresa gracias a esto?”**

Evitar limitarse a describir la herramienta.

Modelo útil:

**Antes:** situación o fricción reconocible.

**Con Agendic:** capacidad concreta.

**Después:** forma de trabajar más sencilla, ordenada, automatizada o controlada.

El “después” debe ser proporcional a la funcionalidad.

No convertir una mejora pequeña en una transformación total del negocio.

# 12. Ejemplos prácticos

Cada vez que sea posible, incluir una situación que permita imaginar el uso.

Los ejemplos pueden ser:

## Ilustrativos

Situaciones creadas para explicar una capacidad.

Deben ser plausibles y utilizar exclusivamente hechos confirmados.

Nunca presentarlos como casos reales.

## Reales validados

Historias de clientes o situaciones reales para las que exista información autorizada suficiente.

Pueden incluir nombres, cifras o resultados solo cuando estén expresamente confirmados.

Un ejemplo no debe convertirse en una demostración técnica paso a paso salvo que la pieza sea específicamente formativa.

# 13. Ángulos editoriales

Una misma semilla puede producir varias piezas si cada una aporta un enfoque diferente.

Ángulos habituales:

- tiempo;
- control;
- orden;
- reducción de tareas manuales;
- prevención de errores;
- experiencia del cliente;
- coordinación del equipo;
- ocupación o aprovechamiento de recursos, solo cuando la relación esté justificada;
- seguimiento comercial;
- fidelización;
- cumplimiento;
- visibilidad de negocio;
- crecimiento;
- integración entre áreas;
- descubrimiento de una función poco conocida;
- caso práctico;
- consejo de uso.

No variar solo el titular y llamar a eso un contenido nuevo.

# 14. Blog

`blog.md` es la pieza desarrollada del tema para formato blog.

Su función es **explicar y desarrollar** una historia con más profundidad cuando el tema lo merece.

Debe ser suficientemente completa para entender la historia sin leer otras piezas.

El blog es una pieza derivada de la semilla, no la fuente de verdad de los demás canales. LinkedIn, Instagram, X o TikTok pueden existir aunque no haya blog.

Estructura orientativa:

1. titular basado en problema, situación o resultado;
2. apertura que demuestre por qué importa;
3. situación o fricción reconocible;
4. respuesta o forma de resolverlo;
5. qué cambia para la empresa;
6. ejemplo práctico;
7. condiciones relevantes;
8. cómo empezar o dónde continuar, si aporta valor;
9. CTA cuando tenga sentido.

No fijar una longitud rígida.

La profundidad debe responder a la complejidad real del tema.

# 15. Contenidos por canal

Formato:

`canal-NNN.md`

Ejemplos:

- `linkedin-001.md`
- `linkedin-002.md`
- `instagram-001.md`
- `instagram-002.md`
- `x-001.md`
- `tiktok-001.md`

La numeración empieza en `001` y es independiente por canal.

Cada archivo representa una publicación o concepto creativo autónomo.

No son resúmenes automáticos de `blog.md`.

Deben conservar:

- hechos;
- condiciones;
- idea central de la semilla.

Pueden adaptar:

- ángulo;
- apertura;
- ejemplo;
- ritmo;
- profundidad;
- formato;
- CTA.

Metadatos mínimos recomendados:

```yaml
semilla_id: AAAA-MM-NNN
canal: linkedin | instagram | x | tiktok
contenido: NNN
estado: borrador | validado | publicado | archivado
```

# 16. Reutilización y variedad

Una semilla no caduca porque ya se haya publicado una vez.

Puede generar nuevos contenidos meses después cuando exista:

- otro ángulo relevante;
- otro sector;
- otro ejemplo;
- una nueva creatividad;
- una campaña relacionada;
- un momento estacional adecuado;
- una mejora posterior que amplíe la historia.

Antes de crear una nueva semilla, comprobar si el tema ya existe.

Antes de crear `linkedin-004.md`, revisar `linkedin-001.md`, `002` y `003` para asegurar que la nueva pieza aporta una idea o tratamiento diferente.

# 17. Newsletters

Una newsletter no es una concatenación automática de entradas.

Es una edición con:

- una intención;
- una jerarquía;
- un hilo;
- una historia protagonista;
- una selección deliberada de historias secundarias.

Cada edición tiene su propia semilla.

Formato:

`newsletters/AAAA-MM-NNN/`

## Semilla de newsletter

Debe definir, como mínimo:

- `newsletter_id`;
- fecha;
- estado;
- objetivo de la edición;
- destinatario cuando no sea general;
- entrada protagonista;
- entradas secundarias;
- orden;
- hilo editorial;
- CTA principal;
- asunto y preheader, cuando estén decididos.

Una newsletter puede utilizar entradas creadas en meses anteriores.

## Jerarquía recomendada

Por defecto:

1. una historia protagonista;
2. una a tres historias secundarias cuando existan temas suficientes;
3. mejoras pequeñas agrupadas si comparten sentido;
4. una apertura breve;
5. un CTA principal claramente reconocible.

No convertir esta pauta en una obligación numérica.

## Función de una historia dentro de newsletter

La versión newsletter de un tema debe despertar interés y conducir a la siguiente capa de profundidad.

No intentar reproducir el blog completo dentro del correo.

# 18. Prioridad y ciclo de vida

Estados de semilla:

- `borrador`: creada y susceptible de revisión;
- `validada`: enfoque editorial revisado y aprobado;
- `publicada`: existe al menos una pieza publicada basada en ella;
- `archivada`: no debe utilizarse para nuevas piezas sin revisión expresa.

La fuente confirma los hechos del producto.

No convierte automáticamente la semilla en `validada`, porque la decisión editorial también debe ser correcta.

## Prioridad editorial

Puede utilizarse, cuando aporte valor:

- `Alta`: tema con utilidad clara, actualidad o gran potencial de descubrimiento;
- `Media`: útil, pero no urgente ni protagonista;
- `Baja`: válido como apoyo, agrupación o reutilización futura.

No confundir prioridad editorial con importancia técnica.

# 19. Contenido sectorial

Crear primero una historia general siempre que la capacidad sea transversal.

Crear una adaptación sectorial cuando el sector permita explicar mejor:

- el dolor;
- el vocabulario;
- el ejemplo;
- la situación de uso;
- el recurso gestionado.

Una adaptación sectorial no debe inventar funcionalidades específicas para ese sector.

Si cambia el funcionamiento real, ya no es solo una adaptación editorial y debe verificarse como un tema funcional diferente.

# 20. Prueba, cifras y casos reales

Las cifras dan credibilidad solo cuando son reales.

No utilizar números decorativos para hacer que una pieza parezca más convincente.

Para publicar:

- número de clientes;
- porcentaje de mejora;
- ahorro de tiempo;
- aumento de reservas;
- reducción de ausencias;
- incremento de ingresos;
- testimonios;
- nombres de clientes;

la información debe estar explícitamente autorizada y trazable.

Cuando no haya cifra, describir el beneficio cualitativamente.

“Evita tener que repetir esta tarea” es preferible a inventar “ahorra 3 horas por semana”.

# 21. Actualidad, normativa y fechas

Una pieza basada en normativa, calendario, obligación legal o información que pueda cambiar necesita especial cuidado.

Antes de publicarla:

- comprobar que existe una fuente autorizada actual;
- incluir fechas concretas cuando sean relevantes;
- distinguir lo obligatorio de lo opcional;
- evitar titulares alarmistas;
- separar claramente lo que exige la normativa de lo que hace Agendic.

Si la información externa no forma parte de las fuentes autorizadas disponibles, no improvisarla.

# 22. CTA y siguiente paso

Cada pieza debe saber qué quiere que haga el lector después.

El CTA puede avanzar por niveles:

## Descubrir

- conocer la funcionalidad;
- ver un ejemplo;
- leer el blog completo.

## Entender

- consultar cómo funciona;
- revisar posibilidades;
- descubrir casos de uso.

## Utilizar

- revisar la configuración;
- activar o probar una capacidad, solo si el proceso está confirmado;
- seguir una guía.

## Pedir ayuda

- contactar con Atención al Cliente;
- solicitar ayuda para revisar un caso.

No todas las publicaciones necesitan un CTA comercial.

A veces el mejor cierre es una idea útil que aumente el conocimiento del producto.

# 23. Reglas de coherencia

Todas las piezas derivadas de una semilla deben respetar estas reglas:

- un hecho confirmado no puede cambiar entre canales;
- una condición no puede desaparecer si al omitirla el mensaje se vuelve engañoso;
- una adaptación sectorial no puede añadir capacidades;
- un ejemplo no puede convertir una posibilidad en un comportamiento garantizado;
- un titular puede ser más creativo, pero no más categórico que la evidencia;
- si cambia un hecho de producto relevante, revisar la semilla antes de crear nuevas piezas.

# 24. Criterio de calidad editorial

Una pieza está preparada cuando puede responder afirmativamente a estas preguntas:

- ¿Parte de algo que una empresa reconoce o valora?
- ¿Está claro por qué el tema importa?
- ¿El protagonismo está en la utilidad y no en Agendic hablando de sí mismo?
- ¿Se entiende qué capacidad concreta permite ese cambio?
- ¿Todos los hechos están confirmados?
- ¿Las condiciones importantes están presentes?
- ¿Existe un ejemplo o una imagen mental suficiente para entender el uso?
- ¿La promesa es proporcional a la capacidad?
- ¿La pieza aporta algo respecto a contenidos anteriores?
- ¿La profundidad es adecuada al canal?
- ¿El lector sabe qué puede hacer después?

Si la pieza es correcta pero indiferente, todavía no está terminada.

El objetivo no es únicamente evitar errores. Es conseguir que el contenido sea **útil, reconocible y accionable**.
